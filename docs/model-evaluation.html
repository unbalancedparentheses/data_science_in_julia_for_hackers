14 How to know your model is wrong

14.1 The filter that wins by doing nothing

Imagine that we have finished the spam filter from Chapter 4 and a small company agrees to try it. We arrive with good news: our filter is 93 percent accurate! The administrator looks pleased, until someone asks how many unwanted emails it actually catches.

Well, that is an inconvenient question. If only seven out of every hundred messages are spam, a program that sends everything to the inbox is already 93 percent accurate. Our impressive competitor could be a program that does absolutely nothing.

And the mistakes are not equally annoying. Letting an advertisement through might cost someone a few seconds. Hiding a customer’s purchase order could cost the company a sale. Before we celebrate that accuracy number, we have some work to do.

Let’s return to the spam problem and work out how to tell whether our filter is helping. We will make our own small collection of messages, so we can control how spam enters the mailbox and watch what happens when we change the rules. Later, we would have to repeat the evaluation with the mail the company actually receives.

First, let’s generate the messages. Run the following code from the repository root; for this experiment, Julia’s standard libraries are enough.

include("14_model_evaluation/core.jl")
using .ModelEvaluation
mail = synthetic_mail()
rows = split_rows(length(mail.label))

To keep our attention on evaluation, we will give each message an observed signal category from 1 to 4. Think of it as a rough summary of how suspicious its words look. We are taking that signal as given here, rather than training another text classifier. The categories occur with probabilities 0.70, 0.20, 0.08, and 0.02, and their true spam rates are 0.01, 0.08, 0.40, and 0.85. So the mailbox’s expected spam fraction is 0.70*0.01 + 0.20*0.08 + 0.08*0.40 + 0.02*0.85, or 7.2 percent. A particular batch will wander a little around that number because the labels are random.

Of course, we know those rates because we invented the mailbox. Our learner does not get to peek! It estimates them from labeled training messages, adding one spam and one ham observation to each category. This is the smoothing idea we used before: a small group should not make us completely certain that its next message will be spam or ham.

14.2 Three datasets, three jobs

Now, how do we give the filter a fair examination? We divide the messages into three groups: 60 percent for training, 20 percent for validation, and 20 percent for testing. The training messages let us estimate the model’s parameters. The validation messages let us try different decision rules. We put the test messages aside until we have finished making those choices.

score_model = fit_score(mail.signal[rows.train], mail.label[rows.train])
validation_probability = predict_score(score_model, mail.signal[rows.validation])
validation_label = mail.label[rows.validation]

It may be tempting to look at the test results, adjust the threshold a little, and try again. After a few rounds, the results might look wonderful. But what have we learned? We have learned how to adapt to those particular test messages. The word “test” on a variable cannot stop us from using its contents to train the model.

Shuffling works for our invented mailbox because each message is an independent draw from the same mechanism. A real inbox is messier. One campaign might send nearly identical messages all week, and a random split could put copies in both training and testing. If we want to recognize new campaigns, we should keep whole campaigns together when splitting. If we want to know how the filter will behave next month, we should save a later period. The way we divide the data should follow the question we are asking.

14.3 Count the mistakes before compressing them

Let’s count what the filter gets right and wrong. We label spam as 1 and ham as 0, and a positive prediction means blocking a message. A true positive is spam we blocked; a false positive is ham we blocked by mistake. A true negative is ham we delivered, and a false negative is spam that slipped through. These four counts make up our confusion matrix.

validation_counts = confusion(validation_label, validation_probability; threshold=0.5)
validation_metrics = metrics(validation_counts)
baseline_counts = confusion(validation_label, zeros(length(validation_label)); threshold=0.5)
baseline_metrics = metrics(baseline_counts)
(validation_counts, validation_metrics, baseline_metrics)

From those counts, we can calculate four useful quantities:

  • Accuracy: the fraction of all messages classified correctly.
  • Precision: among messages blocked, the fraction that really are spam.
  • Recall: among actual spam messages, the fraction blocked.
  • False-positive rate: among actual ham messages, the fraction blocked.

Notice that precision and false-positive rate ask different questions. Precision starts with the blocked messages; false-positive rate starts with the legitimate ones. Their denominators are different. A filter that blocks everything can have perfect recall, and our lazy filter can have high accuracy by delivering everything when spam is rare. Looking at the confusion matrix makes both tricks much harder to hide.

What happens to our all-ham baseline? Its recall is zero whenever spam is present: it catches none of it. Its precision is a more curious case. Since it blocks no messages, there are no blocked messages among which to count the spam fraction. That ratio is undefined, so the function returns missing. A zero would mean something different.

14.4 Choose a threshold for the actual consequences

Let’s put a cost on the two mistakes. Suppose blocking a legitimate message costs five units, while delivering a spam message costs one. We can change these numbers to suit the company: missing a purchase order and seeing an advertisement need not bother everyone equally.

If our confusion matrix contains \(FP\) false positives and \(FN\) false negatives among \(N\) messages, the average observed cost is

\[\frac{C_{FP}FP + C_{FN}FN}{N}.\]

Now we can try a grid of thresholds and choose the one with the lowest cost on the validation messages. If several thresholds tie, we take the first minimum. Our test messages remain in their envelope while we make this choice.

policy = choose_threshold(validation_label, validation_probability;
                          false_positive_cost=5.0, false_negative_cost=1.0)
policy

We may find ourselves back at the beginning: the cheapest rule can be to deliver every message! With these costs and this finite validation sample, blocking mail might do more harm than good. That does not make our filter useful. It tells us to look again at the costs, the evidence, or the available actions. Perhaps the company would prefer a quarantine folder to a choice between blocking and delivering everything.

Can we work out the threshold without trying a grid? Suppose p is a calibrated probability of spam for the population where we will use the filter. Blocking the message has expected cost C_FP*(1-p), since we pay when it is actually ham. Delivering it has expected cost C_FN*p, since we pay when it is spam. Comparing the two, blocking costs no more than delivering when

\[p \geq \frac{C_{FP}}{C_{FP}+C_{FN}}.\]

With our example costs, the cutoff is 5/6. Our validation search need not land exactly there: we have a finite sample, estimated probabilities, and a grid of possible thresholds. We also allowed only two actions in the calculation. Adding a quarantine folder, human review, or a limit on how many messages people can inspect would change the decision we need to solve.

14.5 Probabilities deserve their own evaluation

So far, we have used probabilities to decide which messages to block. But are those probabilities any good? If we collect messages to which the model assigns a probability of 0.8, we would like roughly eight out of ten to be spam. This agreement between predicted probabilities and observed frequencies is called calibration.

Let’s group the predictions into intervals and compare each group’s mean predicted probability with the fraction that really is spam. This gives us a reliability table. We will keep the number of messages in each group too; we will need it when interpreting the result.

validation_reliability = reliability(validation_label, validation_probability; bins=5)
validation_brier = brier_score(validation_label, validation_probability)
(validation_reliability, validation_brier)

We can also summarize probability errors with the Brier score, the mean of (predicted_probability - label)^2. Smaller is better. Unlike the confusion matrix, this score examines the probabilities before we turn them into decisions at a threshold. Even so, calibration is only part of the story: a model that gives every message the overall spam prevalence can be calibrated without telling one message from another.

Suppose one interval contains only three messages. Would we trust its observed spam fraction as much as one based on hundreds? Probably not. The table omits empty intervals, and small groups leave considerable uncertainty. Dividing the same messages into more bins will not magically give us more information. We could use validation data to fit a calibration correction, but then we would need to evaluate that corrected model on untouched data. For now, we are just examining the probabilities we already have.

14.6 A single final evaluation

We have a score model, costs, and a chosen threshold. Let’s leave them fixed and finally open the envelope containing our test messages.

test_probability = predict_score(score_model, mail.signal[rows.test])
test_label = mail.label[rows.test]
test_counts = confusion(test_label, test_probability; threshold=policy.threshold)
test_report = (counts=test_counts, metrics=metrics(test_counts),
               cost=mean_cost(test_counts; false_positive_cost=5.0, false_negative_cost=1.0),
               brier=brier_score(test_label, test_probability))
test_report

Now we can give the administrator a more useful report: which mistakes the filter made, what they cost, and how well its probabilities behaved. The size of the test set and its number of spam messages belong in that report too. A fresh batch from our generator will give somewhat different answers. To estimate uncertainty with resampling, we must preserve the data’s independent units: if whole campaigns are independent, we should resample campaigns rather than individual messages.

What if these results give us an idea for a better filter? Good! We can pursue it, but the test messages have now helped us make another modeling choice. The next version needs a new final examination, perhaps using mail from a later period.

14.7 Change the population, not just the threshold

Suppose the company starts receiving much less spam. Can we keep using the same threshold? Open 14_model_evaluation/14_model_evaluation.jl in Pluto and let’s try it. The notebook estimates error rates separately for spam and ham using validation messages, then calculates expected counts for 1,000 messages at a prevalence we choose. These counts can be fractional because we are calculating averages over possible mailboxes.

For this experiment, we change the fraction of spam while keeping the distribution of scores within spam and within ham fixed. This assumption is called label shift. At a fixed threshold, recall and false-positive rate then stay the same, while precision and average cost change. If spammers also start writing different kinds of messages, the score distributions may change too, and this calculation will no longer describe the whole problem.

Try making blocked ham very expensive. Then make spam rare. How much precision do we lose at the same false-positive rate? Does a threshold chosen for one mailbox still look sensible in another? Keep track of which assumptions you changed along with the numbers; they are what make the experiment interpretable.

14.8 What to carry into the next project

We started with a filter boasting 93 percent accuracy and discovered that the number alone told us very little. Working through the mailbox gave us a better approach: begin with the decision, compare against a baseline, and split data according to the future situation we want to predict. Training fits the model and its transformations; validation helps us choose; testing gives the final estimate. The confusion matrix, probability checks, and costs each answer a different part of the company’s question.

The next chapter applies the same discipline to a more ordinary-looking problem: a table containing missing values, categories, and delivery times. Ordinary tables can hide extraordinary opportunities to fool ourselves.
